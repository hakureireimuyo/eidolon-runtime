# 端口、绑定与控制信号

> 本文档定义节点端口的两类绑定语义,以及"真正的信号"——控制信号。
> 相关文档:[图运行时总纲](./graph-runtime-overview.md) · [执行模型](./graph-execution-model.md) · [节点类型](./graph-node-types.md) · [应用模式与场景图式](./graph-application-patterns.md)

## 1. 核心命题

> **连线 = 数据流动与触发方向(推);内嵌绑定 = 开火时读取的对象(拉)。两种机制,不互相污染。**

## 2. 端口双绑定模型

端口除了连线,还有**内嵌绑定**——声明在接口上、编辑器可见,但不构成"流":

| 端口 | 绑定种类 | 语义 |
|------|---------|------|
| 输入 | 连线 | 参与就绪等待;上游输出满足/唤醒该端口 |
| 输入 | 默认常量 | 即时满足,值为常量;不参与就绪等待 |
| 输入 | 全局读取 | 即时满足,**开火时取全局变量最新值**;不参与就绪等待 |
| 输出 | 连线 | 每轮必发(可 None),推给下游 |
| 输出 | 全局写入 | 每轮开火时写入命名的全局变量 |

本节描述**数据端口**;控制端口的绑定与默认电平见 §4。

**就绪规则**:只有未屏蔽的**连线**数据输入参与"等待所有输入"(见 [执行模型](./graph-execution-model.md) §2.3);引用与常量端口从第 0 轮起即时满足。

无连线、无默认、无引用的**裸端口** → 编辑事务校验报错(强迫显式;可显式声明默认 None)。

## 3. 为什么全局变量不是输出源

全局变量是**状态**,不是输出。它被读取时不产生输出、不唤醒下游:

- 全局被改 → 没有任何节点被触发;
- 读取它的节点在**下一次因其他原因开火时**才看到新值;
- 读取是拉,不是推——全局写入不进入传播,不会产生输入污染。

## 4. 控制信号:与数据严格分离的独立通道

控制信号与数据是**完全不同的两类通道**,端口层强制区分:

| | 数据通道 | 控制通道 |
|---|---|---|
| 端口 | data-in / data-out | control-in / control-out |
| 载荷 | 任意 Python 对象(类型鸭子) | **无载荷,只承载电平**(active / inactive) |
| 连线 | data-out → data-in | control-out → control-in |
| 采样保持 | 是 | 是(电平按轮保持) |

- **交叉连线校验报错**:数据不能流入控制端口,控制信号不能流入数据端口——图层面不允许直连;
- **转换必须经由节点内部**:数据转控制(如比较器:数据入、控制出)或控制转数据(如条件选择)是节点黑盒内部的职责,端口层不混。

### 4.1 控制端口的语义由声明决定

控制信号不携带"含义",含义由**端口声明**决定:

| 声明 | 语义 |
|------|------|
| control-in:门控(enable) | 电平 active = 门开;inactive = 跳过昂贵内部工作(不调 LLM),数据输出照发 None |
| control-in:屏蔽(mask:目标数据端口) | 电平 active = 该数据端口本轮被忽略:屏蔽输入不参与就绪与计算(旁路语义);屏蔽输出不发值,下游保持旧值 |
| control-out | 声明其含义(如时钟节点的方波电平输出) |

### 4.2 默认电平与保持

- 控制端口不连线 → 其**声明的默认电平**生效(类型定义时声明;缺省:门控 = 常开,屏蔽 = 常闭);
- 连线的控制端口:收到第一个电平前用默认电平,此后采样保持最近电平;
- **控制端口不参与数据端口的就绪等待**——电平永远有定义,不存在 warm 问题;
- 屏蔽只作用于数据端口;控制端口不可被屏蔽(断开连线即等效,无需屏蔽机制)。

### 4.3 边界情况

- **全部数据输入被屏蔽**(门开时)→ 节点退化为源节点,每轮自发触发。无需特判——控制信号可以把转换节点临时"解耦"成源;
- **屏蔽 ≠ None**:None 是"节点主动报告无事发生",屏蔽是"输出暂停、下游冻结在旧值"。多数下游对两者反应相同;需要感知新鲜度的节点看数据包时间戳即可区分;
- **费用闸门有两个层次**:控制信号(外部决定能不能开火)+ 节点自身判定(看到数据决定改不改变)。绝大多数轮次里 LLM 节点不产生任何调用费用。

### 4.4 控制信号的来源:缺氧式离散信号网络

控制通道的灵感是《缺氧》自动化系统:**离散信号网络**——机器自己知道什么时候该输出信号,接收端只需要知道"收到信号后做什么",复杂的自动化逻辑不是写进中央控制器,而是由机器 + 导线 + 信号组合出来。

- **控制输出端**:节点内部状态满足某个条件 → 输出电平(如比较器温度超阈值 → `too_hot = active`)。"满足什么条件"完全属于节点自己的实现;
- **控制输入端**:语义统一且简单——门控 active = 门开(工作)、inactive = 跳过昂贵内部工作;屏蔽 active = 目标数据端口本轮被忽略。极性与语义在端口声明中固定,全系统一致;
- 一个节点天然是一个自动化元件:`[比较器]` 数据入、控制出;`[开关]` 玩家操作入、控制出;`[计时器]` 按 tick 状态输出电平;`[战斗系统]` 只暴露 control-in。

### 4.5 基础元件是节点类型资产,不是引擎机制

自动化能力不是引擎写死的,而是由基础元件组合出来的。以下全部是**普通节点类型资产**,运行时对它们零特殊处理:

```
Clock(时钟)  Comparator(比较器)  AND  OR  NOT  Latch(锁存器)
Switch(开关)  Counter(计数器)  Timer(计时器)  Threshold(阈值)  Random(随机)
```

例:温度超过 30℃ 且玩家进入房间时启动空调:

```
[世界温度] → [温度比较器] ──control──┐
                                      ↓
[玩家位置] → [房间判断器] ──control── [AND] ──control──→ [空调]
```

用户同样可以自制 `[剧情条件判断器]` `[任务完成判断器]` `[世界切换判断器]`——对运行时没有区别。**用户编辑的不是"程序",而是在搭建一个可以运行的世界自动化网络**。

### 4.6 数据网络与控制网络的对偶

图中存在两种完全不同的流,在节点内部交汇:

```
                数据网络:  世界状态 ─────→ 节点 ─────→ 世界状态
                控制网络:  条件    ─────→ 节点 ─────→ 条件

        data ────────────────→│            │───→ data
                              │    NODE    │
        control ─────────────→│            │───→ control
```

- **数据流回答**:"世界中有什么、发生了什么、状态是什么。"
- **控制流回答**:"哪些计算现在被允许发生。"
- 数据→控制(比较器)、控制→数据(条件选择)的转换必须经节点内部,端口层不混——与 §4 的交叉连线校验一致。

### 4.7 结构级门控:整段子系统的计算许可

控制信号最大的价值是**结构级门控(computation gating)**——不必让一段子系统里的每个节点每轮自问"现在是不是战斗?",而是在入口处明确告诉它:**这一整段系统现在没有运行资格**。

```
剧情状态 → [条件节点] ──control──→ [战斗系统]
                                     │
                                     ├→ [战斗状态] → [敌人 AI] → [行为规划]
                                     └→ [LLM] → [动作生成] → [世界状态更新]
```

`enable = inactive` 在节点实现**之前**被运行时拦截:节点不执行内部计算、不产生正常数据输出、内部状态不更新。对 LLM 节点这意味着**不进入 prompt 构建、不进入 API 调用、不产生 token**——这不仅是语义上的关闭,也是实际的成本门控。

### 4.8 V1 语义收敛

V1 严格控制信号语义,只保留两类:

```
control-in
    ├── enable(门控整节点)
    └── mask(data-input)(屏蔽指定输入)
```

**不**引入 pause / cancel / reset / flush / priority / interrupt / force / abort 等——它们很容易把控制信号逐渐变成第二套事件系统。原则:

> **数据负责传递世界内容,控制负责决定计算是否发生。**

### 4.9 反模式:数据伪装成控制

不用控制信号、改在数据里塞 `{enabled: false, payload: ...}`,会让每个节点都出现 `if not input.enabled: return`——**控制逻辑重新隐藏进节点内部**,与"一切显式"原则冲突。有了独立的控制通道,图的视觉结构本身就表达"数据从哪里来,以及这个节点什么时候允许工作",用户不需要读代码就能理解整个世界何时运行什么系统。

**世界语义与计算语义的边界**,最终归结为:

- `data: world.reality = MEAT`(世界现在是不是血肉世界)→ 数据,可以被任何节点读取;
- `control: meat_system = active`(血肉世界相关计算现在是否运行)→ 控制,只决定计算许可;

两者即使最终都表现为 `true / false`,也不能因此合并。

## 5. 可编排的控制模式

- 旁路某段数据处理:屏蔽其输入,节点按部分数据工作;
- 暂停一条链:屏蔽链上某输出,下游冻结在旧值,世界其他部分继续转;
- 给反馈环调速:用方波信号周期性屏蔽反馈边;
- 临时解耦:屏蔽全部输入,节点变为自发源;
- 章节门控:按剧情状态启用/关闭整段子系统(战斗、解谜、特殊世界)——多个系统**同时存在于图中,只有满足条件的计算网络被启用**,而不是在程序里写 `if`(实例见 [应用模式与场景图式](./graph-application-patterns.md) §6 双世界)。

全部是连线,不是新原语。

## 6. 校验相关

- 端口绑定合法性:裸数据端口报错;绑定必须指向已声明资产;
- 连线 kind 匹配:data→data、control→control,**交叉连线报错**;
- 引用存在性:绑定引用的全局变量/常量必须已声明,否则提交校验抛异常(见 [资产系统](./graph-assets.md));
- 完整校验清单见 [持久化与编辑](./graph-persistence-and-editing.md) §5。
