# 引擎核心:上下文流动的管理者

> 本文档回答一个问题:**在「程序生成真实结果、LLM 翻译为文字」的架构中,谁是运行的核心、数据如何流动。**
> 相关文档:[运行时核心设计](./runtime-core-design.md) · [状态模型、上下文管理与缓存](./state-and-context.md)(另见:叙事游戏引擎架构与 AI 职责分离)

## 1. 核心命题

> **引擎是管理上下文流动的核心层级:程序决定发生什么,LLM 决定如何表达,引擎决定谁的数据何时流向谁。**

生成器层(对话、剧情、环境等)把 LLM 调度封装为独立可输入输出的对象,但生成器只是"表达器官"。生成器的输入从哪来、输出到哪去,由更底层的概念管理——**引擎**。基础的事件循环、数据流动,都建立在引擎之上。

## 2. 概念模型:LLM 是渲染,引擎是游戏引擎本体

```
游戏引擎:   程序模拟规则 → 引擎更新状态 → 渲染器生成画面
本引擎:     程序模拟规则 → 引擎编排数据流动 → LLM 渲染为文字
```

- 游戏引擎中,物理与逻辑模拟是运行核心,渲染器只是把结果画出来;
- 本项目中,程序规则产生的结果(世界状态、事件、关系变化)是运行核心,LLM 把这些结果**翻译**成文字;
- 真正的运行核心不是 LLM,而是引擎——LLM 类比渲染器:重要,但可换、可关(表现层开关),不承载真实性。

## 3. 引擎的两个职责

| 职责 | 含义 |
|------|------|
| **程序数据注入生成器** | 程序产生的结构化结果(状态、事件、规则判定)由引擎送入生成器,成为生成器的输入 |
| **生成器结果交叉组合** | 各生成器的输出由引擎收集、组合、再分发——一个生成器的产物可以成为另一个生成器的输入 |

引擎不实现生成逻辑(那是生成器的职责),不定义世界规则(那是程序的职责),它编排这两者之间的流动。生成器间上下文交叉输入正是"结果交叉组合"职责的体现——由引擎行使,而非生成器之间自行对接。

## 4. 上下文流动:四个方向

引擎的输入侧同时向程序与 LLM 开放,输出侧把 LLM 的结果送回程序:

```
程序 ──结构化结果──→ 引擎 ──注入──→ 生成器 ──调用──→ LLM
程序 ←──指令/结果── 引擎 ←──输出── 生成器 ←──文字── LLM
```

1. **程序 → 引擎**:程序产生的输入(状态变化、事件、判定结果);
2. **引擎 → 生成器**:把程序结果注入生成器,成为生成上下文;
3. **生成器 → 引擎**:LLM 产生的输出(文字与结构化意图)回到引擎;
4. **引擎 → 程序**:LLM 输出中的指令部分由引擎路由回程序,由程序验证与执行。

## 5. 双向交互:LLM 可以反向指挥程序

LLM 不只是输出文字,同样可以反向向程序输入指令实现交互:

- 角色产生"打开门"的意图 → 引擎把意图路由给程序 → 程序验证(门存在吗?上锁吗?)→ 客观事实回流入引擎 → 再注入生成器成为新的上下文;
- 与「角色认知 vs 世界运行」分离一致:角色可以产生错误的意图,世界不会产生错误的事实(见叙事游戏引擎架构文档的 Action Intent → World Event 循环)。

引擎中可以运行很多程序——编排、交互,让 LLM 将结果变为文字;反之 LLM 的指令也经由引擎回到程序。引擎是这条双向链路的唯一交汇点。

## 6. 与既有概念的关系

| 概念 | 定位 | 与引擎的关系 |
|------|------|-------------|
| 程序 | 真实性的来源:状态、规则、事件 | 程序运行于引擎之上,其输入输出经由引擎 |
| 生成器 | 表现力的器官:LLM 调度的功能封装 | 引擎管理生成器的输入注入与结果组合 |
| 会话 | 高于 LLM 会话的容器(一个角色一个会话) | 引擎在会话边界内编排各生成器的流动 |
| 上下文分层与编译 | 上下文的"内容管理"(放什么、什么顺序) | 引擎是"流动管理"(谁的数据何时流向谁),二者正交 |

## 7. 边界与契约

- **引擎不拥有真实性**——发生什么由程序规则决定;
- **引擎不拥有表现力**——如何表达由 LLM / 生成器决定;
- **引擎拥有流动**——数据从谁流向谁、何时流、以什么形式流,是引擎的职责,也是引擎存在的全部理由;
- 引擎对生成器只管理输入输出,不实现生成逻辑;对程序只做编排与路由,不定义世界规则。
