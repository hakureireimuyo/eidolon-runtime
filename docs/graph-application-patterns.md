# 应用模式与场景图式:同一计算模型的不同实例

> 本文档收录图运行时支撑的典型应用场景及其图式:**一对一聊天、一对多聊天、角色自聊天、多线剧情、探索、解谜、双世界切换、小说知识检索,都是同一计算模型的图拓扑实例,可以自然组合**——新玩法不需要新的 Runtime 功能。
> 相关文档:图运行时总纲(`eidolon-graph` 仓库 `docs/graph-runtime-overview.md`) · 端口、绑定与控制信号(`eidolon-graph` 仓库 `docs/graph-ports-bindings.md`) · [人格、意图与认知链](./graph-cognitive-chain.md) · [表现状态与输出适配](./graph-presentation-output.md)

## 1. 核心命题

> **应用场景共享同一个计算模型,因此它们之间可以自然组合。只要新玩法能够表达为节点、状态、信号和图,它就已经是这个引擎的一等公民。**

"并发本身就是图结构"——不需要多线剧情管理器、群聊机制、双世界管理器之类的特殊系统;它们只是不同的节点组合方式。

## 2. 聊天形态

**一对一聊天**只是最小闭环:

```
用户输入 → 角色状态 → 上下文构建 → LLM → 角色输出 → 世界状态
```

**一对多聊天**只是把输出扇出:

```
                         ┌→ 角色 A
用户输入 → 世界状态 → 分发 ┼→ 角色 B
                         └→ 角色 C
```

**角色之间自动聊天**不需要增加"群聊"机制:

```
角色 A 决策 → A 发言 ─┐
                      ├→ 对话分发 → 角色 B
角色 B 决策 → B 发言 ─┘             ↓
                                 世界状态
```

角色发言经世界状态被其他角色感知,再触发各自决策——这正是 [人格、意图与认知链](./graph-cognitive-chain.md) §3 的 `Alice → Intent → World State → Bob → Intent` 因果链;循环是连线的涌现,不是系统原语。

## 3. 多线剧情

不同剧情线拥有不同的节点链,同时共享某些世界状态:

```
                    ┌→ 剧情线 A ─→ 事件 A
世界状态 ───────────┼→ 剧情线 B ─→ 事件 B
                    └→ 剧情线 C ─→ 事件 C
```

- **并发本身就是图结构**,不需要"多线剧情管理器";
- 剧情章节用控制信号门控:世界状态 → 条件 → control → 各章剧情系统(见 端口、绑定与控制信号(`eidolon-graph` 仓库 `docs/graph-ports-bindings.md`) §5 章节门控);
- "是否触发该事件"由规则节点判定,LLM 只能负责"这个已经确定发生的事件应该如何表现"——**设计权在图上,不在 LLM 手上**。

## 4. 第一人称探索

```
用户行动 → 行动解析 → 世界状态 → 场景状态 → 可见对象筛选
→ 上下文构建 → LLM → 第一人称描述 → 用户
```

- 地图、物品、背包**全部是节点中的数据**(状态字段与资产),不设特殊系统;
- 背包本质是一个状态字段:`inventory = ["knife", "pill", "key_hospital"]`;物品是资产;`[UseItem]` 只是一个"读取玩家状态和动作、然后修改世界状态"的普通节点;
- 场景生成不必"让 LLM 凭空生成":世界状态 → 场景规则 → 场景模板 → 动态状态 → 场景节点 → LLM 表现,生成能力受世界规则约束。

## 5. 解谜

```
玩家输入 → 命令解析 → 规则验证 → 谜题状态 → 世界状态变化 → 描述生成
```

- **"玩家有没有解开谜题"由规则节点决定,不是 LLM 决定的**——因此可以真正设计一个谜题,而不是让模型凭上下文"猜测自己应该怎样解释谜题";
- 谜题状态本身是世界状态(`puzzle.door_unlocked = false` 等),跨场景、跨世界切换都不丢失;
- 整个谜题是一个确定性的状态转换系统,LLM 只负责把已确定的结果呈现给玩家。

## 6. 双世界切换(Fran Bow 式)

"吃药后进入血肉世界"不需要任何特殊机制——它只是一个状态维度经过图传播后,改变了后续节点读取的数据:

```
[药物节点] → world_layer = "meat"
      │
      ▼
[世界状态节点]
      │
 ┌────┴────┐
 ▼         ▼
[地图节点] [物品节点]
      │
 └────┬────┘
      ▼
[上下文构建节点] → [LLM]
```

- 所谓"世界变成血肉",不是让 LLM 想象一个血肉世界,而是**选择另一套确定的数据**:地图 / NPC / 物品 / 描述 / 解谜条件发生变化,Context 节点重新组装当前可见世界,LLM 表现;
- 地图资产可以是**共享结构 + 覆盖层**的世界状态变体系统:`Hospital { common, normal, meat }`——`normal.room_A.description` 与 `meat.room_A.description` 各自存在;
- **两个世界从一开始就都存在,只是其中一个世界的计算网络当前没有被启用**——`control: meat_system = active/inactive` 门控血肉地图、血肉 NPC、血肉解谜等整段子系统,而不是在程序里写 `if drug_taken`(世界语义 vs 计算语义的边界见 端口、绑定与控制信号(`eidolon-graph` 仓库 `docs/graph-ports-bindings.md`) §4.9);
- **世界知道自己是什么**:LLM 不需要知道整个世界,只需要知道当前 tick 通过图流到它的世界切片——引擎不要求渲染器理解整个游戏,它只把当前需要渲染的场景状态交给渲染器;本引擎把这一原则从图形渲染推广到了叙事渲染。

## 7. 小说知识检索与事实验证

一本小说作为知识资产(管线见 资产系统(`eidolon-graph` 仓库 `docs/graph-assets.md`) §2.2),图内按需检索:

```
角色状态 ───────┐
世界状态 ───────┤
当前事件 ───────┼→ 检索节点 → Context Compiler → LLM
当前地点 ───────┤
用户问题 ───────┘
```

- 小说不是被塞进巨大 Prompt,而是**世界知识的一种外部只读数据源**;
- 同一知识资产被不同节点以不同方式消费:角色记忆节点、角色背景检索节点、世界观检索节点、剧情验证节点、对话上下文节点;
- 可组合出**事实验证节点**:

```
LLM 生成候选内容 → 事实提取 → 小说知识库检索 → 事实验证
                                        ┌───┴───┐
                                      一致      不一致
                                       ↓          ↓
                                     接受       修正/拒绝
```

LLM 不再是唯一的知识裁判——AI 可以负责推理,但不能天然拥有世界的真实性。

## 8. 完整组合:交互小说

上述模式自由组合,构成一个完整的可运行世界:

```
                  ┌──────────── 世界时钟
                  │
                  ├──────────── 世界模拟
                  │
玩家输入 → 行动解析 → 世界状态 ─────→ 剧情状态机
                  │                    │
                  │                    ├→ NPC A
                  │                    ├→ NPC B
                  │                    └→ NPC C
                  │
                  ├→ 场景生成
                  │
                  ├→ 记忆检索
                  │
                  └→ 小说知识检索
                           ↓
                     Context Compiler
                           ↓
                          LLM
                           ↓
                       表现输出
```

与此同时 NPC 可以自己运行、剧情可以继续推进、世界时间可以继续走、某个角色可以在后台发生事件——**用户只是其中一个输入源**。此时它已经不像聊天机器人,而接近本来的目标:一个可以被用户设计、编辑、保存、分发和运行的世界模拟器;"聊天"只是这个世界的一种观察和交互方式。
