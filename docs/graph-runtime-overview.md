# 图运行时总纲:节点、信号与世界蓝图

> 本文档定义系统核心的定位:**运行时是一个图运行时——用户编辑的图就是世界的运行蓝图,引擎解释它、世界照着它运转。**
> 相关文档:[执行模型](./graph-execution-model.md) · [端口、绑定与控制信号](./graph-ports-bindings.md) · [节点类型](./graph-node-types.md) · [资产系统](./graph-assets.md) · [持久化与编辑](./graph-persistence-and-editing.md) · [人格、意图与认知链](./graph-cognitive-chain.md) · [应用模式与场景图式](./graph-application-patterns.md) · [表现状态与输出适配](./graph-presentation-output.md)

## 1. 核心命题

> **系统是一个游戏引擎:引擎运行用户编辑的规则,世界按照被设计的意图运转。管理的主体不是资源,而是文本、数据、规则与能力节点。**

```
游戏引擎:   用户编辑场景 → 引擎运行规则 → 渲染器生成画面
本系统:     用户编辑图 → 引擎运行规则 → LLM 渲染为文字
```

- 游戏引擎中,场景是用户编辑的产物,引擎解释并运行它;
- 本系统中,**图(用户编辑的产物)就是世界的运行蓝图**,引擎是图解释器;
- LLM 只是图中的一类节点(表现器官),可换、可关,不承载真实性——与既有文档"LLM 是渲染器"的定位一致。

### 1.1 内核抽象:一个统一的计算模型

过去分别讨论的"世界状态怎么存""事件怎么传播""Processor 怎么调度""LLM 怎么参与""上下文怎么管理""剧情怎么触发""Agent 怎么协作""工具怎么调用",现在都退化为同一个问题:

> **一个节点接收数据和控制信号,根据自身状态产生新的数据和控制信号;图决定这些状态转换如何连接;运行时负责按照统一的时间语义推进整个图。**

各职责被压进一个非常小的边界,**五个分离**:

| 职责 | 承担者 |
|------|--------|
| 传播 | 连线 |
| 转换 | 节点 |
| 事实 | 节点状态 |
| 规则 | 资产 |
| 时间 | tick |

于是"剧情系统""人格系统""记忆系统""世界模拟系统""Agent 系统"不需要成为五套不同的引擎机制——它们只是**不同的节点组合方式**。多 Agent 也不需要特殊的 Agent Manager:所谓 Agent,只是一个包含状态、感知、决策和行动节点的子图。

### 1.2 四个视角,四层界面

| 视角 | 面对的对象 |
|------|-----------|
| 节点实现者(Agent 开发者) | Node Protocol(端口 + 状态 + 配置) |
| 架构设计者 | Graph(拓扑、连线、绑定) |
| 用户 | Graph Editor(可视化编辑) |
| LLM | 某一个具体 Node 的输入输出 |

Scheduler 不需要知道"这是剧情节点、人格节点、Agent、记忆、LLM、世界模拟还是数据库",它只需要知道:Node / Input / Output / State / Control / Tick。

### 1.3 核心对象:可执行的世界

> **系统的核心对象不是 AI,而是可执行的世界。** 角色只是世界中的一种实体,剧情只是世界中的一种规则,Agent 只是世界中的一种动态结构,LLM 只是世界中的一种计算能力。

用户最终拿到的不再是一个"角色卡",而是一个**可执行世界**:角色卡只是最小规模的世界资产,完整 RPG 是更大的图,互动小说是另一种图,Agent 社会又是另一种图。新玩法只要能够表达为节点、状态、信号和图,就已经是这个引擎的一等公民——**不需要为新的玩法设计新的 Runtime 功能**。

## 2. 核心概念

| 概念 | 含义 |
|------|------|
| **图** | 世界运行蓝图:节点实例 + 连线 + 绑定,是用户编辑的产物 |
| **节点** | 状态转换器:读输入、改自身状态、写输出;内部实现黑盒(程序或 LLM) |
| **数据包(数据通道)** | 沿数据连线流动的数据;数据到达 = 触发 |
| **控制信号(控制通道)** | 无载荷的电平信号:门控与屏蔽,与数据严格分离 |
| **连线** | 数据流动方向 = 触发方向;一条输出可扇出到多个输入 |
| **节点内部状态** | 节点自维护的数据("权重"),世界事实的分布式存储 |
| **资产** | 命名的声明式对象:全局变量、常量、节点类型、图 |
| **轮次(tick)** | 世界的心跳;每轮全图同步推进一拍 |

## 3. 与既有设计文档的关系

图模型不是推翻既有架构,而是它的落地形态:

| 既有概念 | 图模型中的对应 |
|---------|--------------|
| Processor(状态转换器) | 节点 |
| Event(状态变化的原因) | 信号(数据包) |
| State Store(共享状态) | 分布式:节点内部状态 + 全局变量资产 |
| Event Bus(事件分发) | 连线传播(用户显式设计的分发路径) |
| 引擎 = 流动的管理者 | 图运行时:连线的解释者 |
| Context Compiler | 普通节点(子图):数据 → 上下文 |
| LLM 反向指挥程序 | 工具调用节点 / 程序验证节点 |
| Agent | 节点子图:状态 + 感知 + 决策 + 行动节点 |
| Scheduler / Planner | 图中的调度节点(时钟、条件、计划) |
| Tool | 能力节点(声明 ToolSpec 的普通节点) |
| RAG / 记忆检索 | 检索节点(知识资产 → 相关片段) |
| 记忆系统 | 记忆节点(写入 / 压缩 / 检索) |
| 世界模拟 | 模拟节点 |
| 剧情系统 | 剧情图 |
| 场景生成器 | 场景节点 |
| 输出呈现 | 输出节点(表现状态 → 输出适配器) |

与演化路线的关系:一至三阶段(State/Event 骨架、多处理器协同、反向控制流)在图模型中统一为"建图";四阶段(Extension Registry)即节点类型资产;五阶段(Scheduler/Planner)是图中挂载的调度节点;六阶段(多模态)是新的昂贵节点类型。图运行时自身的落地顺序另有"阶段零:最小验证闭环"(见 [演化路线](./evolution-roadmap.md) §4.0)。

## 3.1 世界知识的四层分离

图模型把"这个世界"拆成四种信息,各有明确的来源与生命周期:

| 层 | 回答的问题 | 载体 |
|----|-----------|------|
| **世界状态** | 现在发生了什么 | 节点状态 + 全局变量(世界快照) |
| **规则图** | 什么情况下允许发生什么 | 图资产(节点 + 连线 + 绑定) |
| **知识库** | 这个世界本来是什么样 | 知识资产(如小说向量库,外部只读数据源) |
| **LLM** | 如何把已经确定的东西表达出来 | 表达节点 |

- 世界观/人物设定/小说原文不必塞进一个越来越长的巨大 Prompt——它们成为**世界知识的一种外部只读数据源**,按需检索注入;
- **世界事实与世界知识分离**:状态回答"发生",规则回答"允许",知识回答"设定",三者都不由 LLM 产生;每一种信息都有明确的来源与生命周期,这比单纯增加 Prompt 长度更稳定;
- "AI 可以负责推理,但不能天然拥有世界的真实性"——LLM 生成的内容可经**事实验证节点**回流校验(见 [应用模式与场景图式](./graph-application-patterns.md));
- 同一知识资产可以被不同节点以不同方式消费:角色记忆节点、角色背景检索节点、世界观检索节点、剧情验证节点、对话上下文节点各取所需。

同理,应用场景也是组合的结果:一对一聊天、一对多扇出、角色自聊天、多线剧情并发,都是同一计算模型的图拓扑实例——**并发本身就是图结构**,不需要额外的"多线剧情管理器""群聊机制"(实例见 [应用模式与场景图式](./graph-application-patterns.md))。

## 4. 循环是连线的涌现,而非系统原语

- 图**没有**强制的起点和终点:起于信号源(时钟、聊天输入、动作输入),终于吸收(节点不改变或输出不再被消费);
- **循环不是引擎强加的自循环,而是用户连线的产物**:一条反馈连线就是一个循环,没有反馈连线就没有循环;
- 拓扑层不设限:死循环、无源环、纯反馈环都是合法的用户设计,引擎不禁止;
- 执行器只保底"不挂起"(见 [执行模型](./graph-execution-model.md)),编辑器只做静态提示(无源环永不自发触发、无门控环每轮空转),提示不是禁止。

## 5. 节点内部是黑盒,LLM 只是节点的一种

- 节点对外只有契约:输入端口、输出端口、状态与配置字段。内部是程序还是 LLM、是单节点还是嵌套子图,一概无关;
- LLM 节点只是"昂贵的节点":不关心数据在哪,只关心被传入了什么、传给哪个接口、产出什么;
- **上下文管理是一条可编辑的节点链**:

```
[状态节点们] →(可选:RAG / 向量检索 / 记忆压缩)→ ContextManager 节点 → LLM 调用节点
```

"被管理上下文注入"因此完全可见:LLM 能收到什么,看它的上游连线即可,没有隐藏通道。链上接什么(要不要记忆压缩、接几个检索)是用户的编辑。

## 6. 被否定的方案

- ❌ **直接依赖 LangGraph**:per-invocation 执行(世界需要无人调用时持续运转)、以 LLM 调用为中心的节点编排(LLM 应是节点之一而非节点之核)、编译期静态图(世界规则需可编辑为数据)。借用其"图与状态"的范式,自研执行内核。
- ❌ **共享黑板(Blackboard)**:数据写入的消费时机不确定,链路不显式。改为:数据随信号沿连线流动,节点内部自维护状态。
- ❌ **强制单一入口/出口**:改为任意信号源与吸收点,循环由连线涌现。
- ❌ **以"人格内核(Personality Core)"为系统本体**:人格、记忆、情绪、世界、剧情全部围绕一个不可替换的核心组织,世界规则没有一等公民位置,每新增一种需求都要定义"如何向核心产生事件"——外部世界沦为模糊的能力垃圾桶,事件同时承担数据传播、状态变化、因果关系、调度与通信多个职责。图模型把职责重新压回边界:人格是可编辑子图 + 资产(见 [人格、意图与认知链](./graph-cognitive-chain.md)),事件只是沿连线传播的数据包。

## 7. 核心原则汇总

1. **规则与事实分离**:图(规则)是资产,节点状态(世界事实)是快照,分开存储;改图不动事实。
2. **一切显式**:数据链路、读取引用、控制信号全部可见于图,没有隐藏通道。
3. **确定性优先**:同步轮次 + 轮初读轮末提交,节点执行顺序与结果无关。
4. **节点协议是唯一边界**:实现节点协议 = 注册为能力,运行时只认接口不认实现。
5. **职责五分离**:连线负责传播,节点负责转换,节点状态负责事实,资产负责规则,tick 负责时间——系统只需要稳定这五个概念,其余全部是节点组合。
